# toolbox ソフトウェア要件

元の企画書：[requirements.md](requirements.md)。技術構成と採用理由は [software-stack.md](software-stack.md)、手順は [development.md](development.md) を参照。

## 目的

PC の中で完結する便利ツールを1つの toolbox にまとめ、版番号付きの zip として同僚に配る。どれが最新版か分からない状態と、zip 作成・版番号付けの手作業をなくす。

## 利用者

- 使う人：数人の同僚。会社の Windows PC または Mac で、Chrome か Edge を使う。
- 作る人：本人。ツールの開発、版を出す操作、zip を渡すことを行う。

## 主要な利用の流れ

1. 作る人がツールを直し、toolbox リポジトリへ push する。
2. 作る人が CLI または GitHub の画面で、日付形式の版（例：`2026.10.18`）のリリースを作る。
3. 自動処理が全体を検証・ビルドし、`toolbox-2026.10.18.zip` をリリースに添付する。
4. 作る人がその zip をダウンロードし、同僚に直接渡す（手作業のまま）。
5. 同僚は zip を解凍し、`index.html` を Chrome か Edge で開き、ホームからツールを開いて使う。ファイルや文章をホームに置く・貼り付けると、使えるツールで開ける。

## 扱う範囲 / 今は扱わないこと

扱う

- ホーム（ツールのタイル一覧、アイコン、表示名、説明、作業中の様子、版番号）と、タイルの並べ替え・表示（使う人ごと）
- ホームに置いた・貼り付けたもの（ファイル・フォルダ・文章・画像）を、受け取れるツールで開くこと
- 各ツール（プロンプト集・画像変換・PDF編集・ローカルノート・文字コード変換・タイピングゲーム）と、ツールの間の作業の受け渡し
- 開いたツールの作業内容を、ほかのツールへ移っても保つこと
- 入口とツールで揃えた見た目（配色・文字・部品）、ライト・ダークの表示と切り替え、ファイルのドラッグ＆ドロップ・ダウンロードの基本動作
- リリースを作ると zip ができる自動処理

今は扱わない

- カテゴリ分け、検索、更新履歴
- 自動更新や新しい版の通知
- 社外公開、社内サーバーへの配置
- Safari への対応
- ツールごとの版番号や、ツール単体での配布
- 各ツールの要件にある「今は扱わない」もの

## 必要な機能と主要な振る舞い

### 1つのアプリ

- 全ツールを1つの HTML に入れる。配布物は `toolbox-<版>/index.html` の1ファイルだけにし、zip の名前は `toolbox-<版>.zip` とする。中の名前は英数字と `-` `.` だけにする。
- 画面は URL のハッシュ（`#/<ツールの id>`）で表し、ブラウザーの戻る・進むでも移れる。`file://` で動く方法に限る。
- 一度開いたツールは、ホームやほかのツールへ移っても作業内容を保つ。保存していない作業があるツールは、ホームのタイル・切り替えメニュー・タブの題名に印を付ける。閉じると失う作業があるときは、ページを閉じる前にブラウザーの確認を出す。
- 1つのツールの不具合で、ほかのツールやホームを止めない。

### ホーム

- ツールのタイル（アイコン・名前・説明・作業中の様子）を並べ、版番号を表示する。並べ替えと表示・非表示は使う人が変えられ、その PC のブラウザーに残し、新しい版でも保つ。新しい版で増えたツールは表示し、並べ替え済みなら最後に置く。
- ファイル・フォルダをドラッグすると、受け取れるツールのタイルを光らせる。タイルに落とせばそのツールで、それ以外に落とせば受け取れるツールで開く。受け取れるツールが2つ以上なら「何をしますか？」で選ばせ、1つならそのまま開く。どのツールも受け取れないものは、理由を知らせる。
- 貼り付けた文章・画像も同じように受け取れるツールで開く。
- 背景にマウスの動きに合わせた細い線の流れを描く。止められ、止めた状態を保つ。操作がない間・ほかのウィンドウを使っている間は静めて止める。動きを減らす設定では描かない。
- 「このアプリについて」で、版、データの扱い、配布物に入ったライブラリのライセンスを示す。

### ツールの共通の形

- 画面上部は共通のヘッダーにする。左上の一角にホームへ戻るボタン、ツールのアイコンと名前（押すとほかのツールへ移るメニュー）、配色の切り替えを並べ、全ツールで同じにする。右側には各ツール固有の操作を置く。右下に版番号を出す。
- タブの題名とアイコンは開いているツールに合わせ、開いているファイル名と未保存の印を付ける。
- ファイルを受け付ける場所以外にファイルを落としても、ブラウザーがそのファイルを開いて作業中の画面から離れないようにする。受け付ける場所では、落とせることが分かる表示を出す。
- ファイルの保存はダウンロードとして行う。元のファイルを上書きするのは、使う人が選んだフォルダを正本とするツール（プロンプト集・ローカルノート）が、保存を確定したときだけにする。

### 表示

- OS のダークモード設定に合わせてライト・ダークで表示する。ボタンで切り替えられ、選んだ表示はホームと全ツール・版をまたいで共有する。OS と同じ表示に戻したら、以後は OS に従う。印刷と、ツールが書き出す文書は常にライトにする。
- 動きは控えめにし、動きを減らす設定では止める。読み上げとキーボードで使える。
- 画面の幅 375px でも横にはみ出さずに使える。

### データの扱い

- 扱うファイル・入力を外部へ送らない。外部との通信そのものを止める。
- ブラウザーの中に残すのは、配色・ホームの並び・背景の流れの設定、選んだフォルダの記録、PDF編集の復元用データ、ローカルノートの表示設定だけにする。どれも版（解凍先のフォルダ）をまたいで読める形にする。

### 版番号

- toolbox 全体で1つの版番号を持つ。形式は日付（`YYYY.MM.DD`）。同じ日に2回目以降の版を出すときは `YYYY.MM.DD.2` のように末尾に番号を付ける。
- 版番号はリリースを作るときに入力したものを使い、ビルド時に埋め込む。ホームの上部と各ツールの右下に表示する。

### 版を出す

- GitHub でリリースを公開すると、版番号の形式の検査 → 全体の総合検証 → 版を付けたビルド → zip の作成 → リリースへの添付が自動で進む。どれかが失敗したら zip は添付しない。失敗は GitHub 上で分かる。

## 開発時の操作

- テスト、テストなしのローカルビルド（zip まで）、総合検証、検証付きの zip 作成を別々のコマンドで実行できる。PR・main への push 時とリリース時の自動検証を行う。具体的な手順は [development.md](development.md) を正本とする。

## 完了条件

1. CLI または GitHub の画面で日付形式の版のリリースを作ると、全体を検証・ビルドし、`toolbox-<版>.zip` がリリースに自動で添付される。本人の手作業はない。
2. 検証かビルドが失敗すると、zip は添付されず、失敗が GitHub 上で分かる。
3. zip を解凍して `index.html` を開くと、ホームに全ツールのタイルと版番号が出て、各ツールを開け、ホームへ戻れ、ツールの右下に同じ版番号が出る。ファイル・フォルダ・文章を置く・貼り付けると使えるツールで開ける。
4. 3 を、会社の Windows PC（Edge）と Mac（Chrome）で、ネットにつながない状態で確認している。

## 制約

- 使う人は何もインストールせず、zip を解凍して `index.html` を Chrome か Edge で開くだけで使える。
- 対象は Mac・Windows の Chrome と Edge 129 以降。最新の安定版を推奨する。
- ネットにつながらない状態でも、ホームと全ツールが動く。CDN や外部サイトには頼らず、必要なものはすべて配布物に入れる。`file://` で動く。
- OS・ブラウザー・Node.js の標準機能、既存ライブラリの公開 API、共通部品を優先し、自前実装は固有要件に必要な部分へ絞る（[実装方針](development.md#実装方針)）。
- リポジトリは private のまま。社内サーバーは使わない。

## 未決事項

- 会社の PC のブラウザやセキュリティ設定で、`file://` の HTML・WebAssembly・Worker・File System Access に制限がないか（未確認）。完了条件4で確かめ、問題があれば方針を見直す。
- 今後追加するツールは未決。

## 実装で決めたこと

- 旧構成（ツールごとの HTML・ツールごとの npm 依存・入口ページの生成）から、1つのアプリへ作り直した（2026-10-18）。理由と技術の選定は [software-stack.md](software-stack.md) を参照。
- ホームの並び順の記録（`toolbox-cards`）・配色（`toolbox-theme`）・背景の流れ（`toolbox-flow`）・プロンプト集の保存先の記録は、旧構成のキーをそのまま使い、作り直した版でも引き継ぐ。ローカルノートとPDF編集の記録は旧構成では配置 URL ごとに分かれていたため、作り直した版から固定のキーにした（作り直した最初の版でだけ、ローカルノートのフォルダを選び直す）。
