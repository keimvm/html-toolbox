# toolbox ソフトウェア要件

元の企画書：[requirements.md](requirements.md)。技術構成は [software-stack.md](software-stack.md) を参照。

## 目的
1ファイルのHTMLで作った便利ツールを一つの toolbox にまとめ、版番号付きの zip として同僚に配る。どれが最新版か分からない状態と、zip 作成・版番号付けの手作業をなくす。

## 利用者
- 使う人：数人の同僚。会社の Windows PC または Mac で、Chrome か Edge を使う。
- 作る人：本人。ツールの開発、版を出す操作、zip を渡すことを行う。

## 主要な利用の流れ
1. 作る人がツールを直し、toolbox リポジトリへ push する。
2. 作る人が GitHub の画面で、日付形式の版（例：`2026.09.26`）のリリースを作る。
3. 自動処理が、一覧ファイルに書かれたツールを検査・ビルドし、`toolbox-2026.09.26.zip` をリリースに添付する。
4. 作る人がその zip をダウンロードし、同僚に直接渡す（手作業のまま）。
5. 同僚は zip を解凍し、`index.html` を Chrome か Edge で開き、一覧からツールを開いて使う。

## 扱う範囲 / 今は扱わないこと
扱う
- 入口ページ（ツールのカード一覧、アイコン、表示名、説明、版番号、対象ブラウザの注意書き）
- 各ツール（ツールの画面の隅にも版番号を表示する）
- リリースを作ると zip ができる自動処理
- pdf-edit を toolbox へ移すこと（最初の版に含める）
- note-html を `tools/note-html/` にまとめ、PDF編集と共通の入口・検証・配布手順へ組み込むこと
- 入口ページと各ツールの見た目（配色・文字・ボタン等の部品）と、ファイルのドラッグ＆ドロップ・ダウンロードの基本動作を揃えること
- OS のダークモード設定に合わせた表示と、画面のボタンによるライト・ダークの切り替え
- 各ツールのヘッダー左上の共通部品（トップへ戻る・ツールのアイコンと名前・表示の切り替え）

## 必要な機能と主要な振る舞い

### ツールの管理
- 全ツールを toolbox リポジトリ1つにまとめ、ツールごとにフォルダ（`tools/<フォルダ名>/`）を分けて開発・履歴を管理する。
- ツールはビルドして1ファイルの HTML を作る形とする（pdf-edit と同じ）。npm の依存関係はツールごとに独立させ、あるツールの更新がほかのツールに影響しないようにする。
- ツール間で揃える見た目と処理は、直下の共通フォルダ（`ui/`）にまとめ、各ツールがビルド時に取り込む。共通フォルダは npm の依存を持たない。共通フォルダを変えたときは全ツールを検証する。

### 共通の見た目と操作
- 入口ページと各ツールで、配色・文字・角丸などの値と、ボタン・入力欄・ダイアログ・フォーカス枠の見た目を揃える。画面の配置は各ツールに任せる。
- OS のダークモード設定に合わせて、入口ページ・各ツール・戻るリンク・版番号をライト・ダークで表示する。印刷と、ツールが書き出す文書（ローカルノートの HTML エクスポート）は常にライトにする。
- 入口ページと各ツールのボタンで、ライト・ダークを切り替えられる。選んだ表示は入口ページと全ツールで共有し、開き直しても保つ。OS の設定と同じ表示に戻したら、以後は OS の設定に従う。
- 各ツールの画面上部は共通のヘッダーにする。左上の一角にトップへ戻るボタン（ホームのアイコンのみ。配布時だけ）、ツールのアイコン（タブのアイコンと同じ）とツール名、表示の切り替えを並べ、全ツールで同じ見た目にする。右側には各ツール固有の操作を置く。
- ファイルを受け付ける場所以外にファイルを落としても、ブラウザーがそのファイルを開いて作業中の画面から離れないようにする。受け付ける場所では、落とせることが分かる表示を出す。
- ファイルの保存はダウンロードとして行い、`file://` で開いた場合も同じ方法で動くようにする。
- 直下の一覧ファイル（例：`tools.json`）に、zip に入れるツールのフォルダ名・表示名・説明を書く。
  - 書いたツールだけが zip に入る。フォルダがあっても書いていないツール（作りかけ・個人用）は入らない。
  - 書いた順に入口ページに並ぶ。

### 版番号
- toolbox 全体で1つの版番号を持つ。形式は日付（`YYYY.MM.DD`）。同じ日に2回目以降の版を出すときは `YYYY.MM.DD.2` のように末尾に番号を付ける。
- 版番号はリリースを作るときに入力したものを使う。
- 入口ページの上部と、各ツールの画面の隅に表示する。ツールへの表示は zip を作るときに書き足し、ツールの元のファイルは変えない。

### 版を出す
- GitHub の画面でリリースを作ると、次の処理が自動で進む。
  1. 一覧のツールごとに、依存関係の取得 → 検査 → ビルドを行う。
  2. 入口ページを作り、各ツールへトップに戻るリンクと版番号を追加する。
  3. zip を作り、そのリリースに添付する。
- どれか1つのツールで検査かビルドが失敗したら zip は添付しない。失敗したことは GitHub 上で分かるようにする。

### zip の中身
```
toolbox-<版>/
  index.html
  tools/
    <フォルダ名>.html
```
- zip の名前は `toolbox-<版>.zip`。中身は版番号付きのフォルダ1つにまとめ、古い版と同じ場所に解凍しても混ざらないようにする。
- zip の中のファイル名とフォルダ名は英数字（と `-` `.`）だけにする。日本語の表示名は画面で見せる。
- 入口ページから各ツールを開ける。
- 各ツールのヘッダー左端、ツール名の手前にトップへ戻るボタン（ホームのアイコン。文言は表示せず、読み上げ名とツールチップを「トップへ戻る」にする）を表示し、同じタブで入口ページへ戻れる。戻り先は `../index.html` とし、ブラウザーの履歴には依存しない。
- 戻るリンクは配布時に追加する。加工前の単体 HTML と開発画面には表示しない。戻る操作でツールの作業状態を削除せず、既存の離脱確認・復元の仕組みを維持する。

## 完了条件
1. GitHub の画面で日付形式の版のリリースを作ると、一覧のツールを検査・ビルドし、`toolbox-<版>.zip` がリリースに自動で添付される。本人の手作業はない。
2. どれか1つのツールで検査かビルドが失敗すると、zip は添付されず、失敗が GitHub 上で分かる。
3. zip を解凍して `index.html` を開くと、次のことができる。
   - ツールのカード一覧（アイコン・表示名・説明）、版番号、「Chrome または Edge で開いてください」の注意書きが表示される。
   - 一覧から各ツールを開ける。
   - 各ツールの左上から一覧へ戻れる。ツールを直接開いた場合や、解凍したフォルダ全体を移動した場合も戻れる。
   - 各ツールの画面の隅にも同じ版番号が表示される。
4. 3 を、会社の Windows PC（Edge）と Mac（Chrome）で、ネットにつながない状態で確認している。
5. 最初の版では、pdf-edit が `tools/pdf-edit/` に履歴付きで移っていて、zip に入っている。

## 制約
- 使う人は何もインストールせず、zip を解凍して `index.html` を Chrome か Edge で開くだけで使える。
- 対象は Mac・Windows の Chrome と Edge 129 以降。最新の安定版を推奨する。
- ネットにつながらない状態でも、入口ページと全ツールが動く。CDN や外部サイトには頼らず、必要なものはすべて zip に入れる。
- `file://`（PC上のファイルを直接開く形）で動く。
- OS・ブラウザー・Node.js の標準機能、既存ライブラリの公開 API、共通部品を優先する。標準・既存依存で足りなければライブラリを検討し、自前実装は固有要件に必要な部分へ絞る。共通化できる部品は `ui/` に集約し各ツールから利用する。
- リポジトリは private のまま。社内サーバーは使わない。

## 未決事項
- 会社の PC のブラウザやセキュリティ設定で、`file://` の HTML を開くときに制限がないか（未確認）。完了条件4で確かめ、問題があれば方針を見直す。
- 現在の配布対象は pdf-edit と note-html。今後追加するツールは未決。
- 手で書いた（ビルドのない）HTML のツールがあるか（未確認）。ある場合は、その扱いを決める。
- 移したあとの元の pdf-edit リポジトリと、その既存のリリース（`v*`）をどうするか（案：アーカイブして残す）。

## 実装時に委ねること
- 一覧ファイルの名前・形式・項目名、入口ページとツールへの版番号表示の見た目と位置、注意書きの文言。
- 上記以外の導線の細部。上の範囲を越える機能は足さない。
- pdf-edit の移し方の細部（履歴を残すことは必須）と、移したあとの文書・CI の整理。
