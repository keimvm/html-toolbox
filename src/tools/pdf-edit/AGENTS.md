## 実装の原則

- 現在の要件を満たす最も単純な実装を選ぶ。仮の将来要件のための抽象化、互換層、フォールバックを作らない。
- 元の PDF には手を加えず、ページの並び・回転だけを持つ（`editor.ts`）。要素の削除も、要素を除いた1ページの PDF を新しい元の文書として開き、ページを差し替える形にする（元の PDF を書き換えない）。
- PDF の処理は toolbox の共有の PDF エンジン（`src/engine/pdf/`）に足す。画像変換も同じエンジンを使うため、変えたら両ツールのテストを確かめる。
- 「PDFを小さくする」はページ直下の画像だけを差し替える（共有の PDF エンジンの `shrink`）。結果は復元用データに入れず、編集の状態（`Editor`）とは別に持つ。理由と確かめた範囲は [技術構成](docs/software-stack.md#pdf-を小さくする画像変換から移す2026-10-18) に書く。
- `Editor` はページを直接書き換えるため、画面の部品は `revision` を読んで描き直す（`@preact/signals` は props の変わらない部品の描き直しを省く）。
- 復元用データは固定のキーで持ち、版をまたいで読めるようにする。配置 URL をキーにしない。
- Markdown 変換と OCR は扱わない。依頼の範囲を越えて実装しない。

## 配布物の制約

- PDF、取り出した内容、ファイル名を外部へ送信しない。アクセス解析や外部フォントも導入しない。
- Worker・WebAssembly・フォントなどを追加したら、それぞれの埋め込みと `file://` での動作を次に検証を指示されたときの確認項目に含める。実行までは未確認とする。
- 業務データや個人情報のある PDF をコミットしない。共有のテストは合成 PDF（`src/engine/pdf/samples.test-support.ts`）を使い、生成方法と期待結果を残す。

## 変更後の確認

- 画面・PDF エンジン・配布方式を変えた場合は、ブラウザーの操作、コンソールのエラー、通信、配布物の `file://` 起動について必要な確認事項を整理し、検証結果を [docs/verification.md](docs/verification.md) に記録する。
- `pnpm check` にはブラウザーでの実行は含まれない。配布物のテストはファイルの構成の静的な検査であり、実行時の通信や PDF の機能の検証とは別。
- 作業記録の画像は Git 管理対象外の `output/` へ保存する。
