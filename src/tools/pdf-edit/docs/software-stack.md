# ソフトウェアスタック検討

検討日：2026年9月19日

[RFP.md](RFP.md)をもとに、対話で合意した初版の範囲と、技術構成の検討結果を記録する。機能の範囲と制約は合意済み。以下の技術構成は検証の第一候補であり、採用は動作確認後に判断する。

## 合意した前提

- 必要なプログラムと補助データをすべて埋め込んだ、単一HTMLを配布する。
- 利用者はインストールせず、HTMLをブラウザーで直接開いて使う。
- 初回から外部サイトの読み込みに依存せず、PDFとその内容を外部に送信しない。
- Mac・WindowsのEdge・Chromeを対象とする。
- 無料で使え、安定性を確認できるライブラリを選ぶ。条件を満たせない機能は保留する。

開発時はソースを複数ファイルに分け、配布時に単一HTMLへまとめる。開発環境での依存パッケージ取得と、利用時のオフライン動作は分けて考える。

## 初版の範囲

| 扱い         | 機能                                                  |
| ------------ | ----------------------------------------------------- |
| 初版で目指す | ページの削除・並べ替え・結合・回転、編集結果のPDF保存 |
| 初版で目指す | ページ全体のPNG・JPEG保存                             |
| 初版で目指す | PDFに含まれる文字情報の取り出し・テキスト保存         |
| 初版で目指す | 要素一覧、画像の情報確認・個別抽出                    |
| 保留         | 画像・ロゴ、文章、罫線・背景などの個別削除            |
| 保留         | Markdown変換、OCR                                     |

画像の情報確認は、解像度やサイズを調べ、必要な画像を取り出して分析・再利用するために行う。確認する情報は、縦横のピクセル数、PDF上での配置サイズ、その配置サイズに対する実効解像度（dpi）とする。

要素一覧の単位や、個別抽出できる画像の対応範囲は未決。文字情報を持たないスキャンPDFの文字認識は、OCRを保留するため初版では扱わない。

RFPで未確認だったオフライン利用は上記の方針で具体化し、要素の個別削除とMarkdown変換は保留に変更した。

## 第一候補の構成

| 担当                             | 技術候補                     | 役割・選定理由                                                   |
| -------------------------------- | ---------------------------- | ---------------------------------------------------------------- |
| 画面・操作                       | TypeScript＋HTML＋CSS        | 標準の画面要素を使い、現在の要件に必要な構成から実装する         |
| PDF表示・ページ編集・文字抽出    | `@embedpdf/engines`のv2系    | 既存の高水準APIを優先して利用し、PDF処理を同じエンジンにまとめる |
| 要素一覧・画像情報取得・個別抽出 | `@embedpdf/pdfium`のv2系     | 高水準APIで足りない操作に、PDFiumの公開APIを利用する             |
| 開発・配布用ビルド               | Vite＋vite-plugin-singlefile | 分割したJavaScriptとCSSを配布用HTMLへまとめる                    |
| 依存パッケージ管理               | pnpm                         | 開発環境でライブラリを管理し、検証したバージョンを固定する       |

PDFiumはPDFの表示や編集を担う処理エンジンで、EmbedPDFはブラウザーから利用するためのWebAssembly版とAPIを提供する。WebAssemblyは、ブラウザー内で実行するプログラム形式の一つ。

EmbedPDFの公式リポジトリは、v3を開発中として、安定版にはv2を案内している。本検討はv2系を対象とする。v2のパッケージはMITライセンスとして公開されている。採用する版に含まれるPDFiumと依存ライブラリのライセンス・必要な表示も確認する。[公式リポジトリ](https://github.com/embedpdf/embed-pdf-viewer)、[v2の説明](https://github.com/embedpdf/embed-pdf-viewer/tree/v2)

## PDF.js＋pdf-lib案との比較

| 観点             | PDF.js＋pdf-lib                                        | PDFium系（EmbedPDF v2）                                                |
| ---------------- | ------------------------------------------------------ | ---------------------------------------------------------------------- |
| 基本構成         | PDF.jsで表示・文字抽出、pdf-libでページ編集を分担      | 表示・文字抽出・ページ編集を同じエンジンで扱う構成を検証できる         |
| 画像の分析・抽出 | PDF.jsの描画命令や画像データを扱う追加実装が必要になる | 画像の寸法・dpi・データを取得する専用APIがある                         |
| 保守面           | pdf-libは新しい公開版が長期間出ていない点を考慮する    | 公式が案内するv2系の安定版と、ブラウザー向けパッケージの動作を確認する |
| 単一HTML化       | PDF.jsの補助プログラム・データを含めた埋め込みが必要   | WebAssembly本体と補助プログラムを含めた埋め込みが必要                  |

画像の解像度・サイズの確認と個別抽出を重視するため、PDFium系の検証を先に行う。EmbedPDF v2のAPI定義には、画像情報取得、画像データ取得、要素列挙、ページ操作に対応する関数が含まれている。ただし、APIの存在だけでは今回の構成での安定動作を保証できない。[PDFium公式API](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/public/fpdf_edit.h)、[EmbedPDF v2のAPI定義](https://github.com/embedpdf/embed-pdf-viewer/blob/v2/packages/pdfium/src/vendor/functions.ts)

比較に用いた資料：[PDF.jsのページAPI](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html)、[pdf-libの機能](https://pdf-lib.js.org/)、[pdf-libの公開状況](https://www.npmjs.com/package/pdf-lib)。

## 単一HTMLへのまとめ方

- Viteとvite-plugin-singlefileで、画面のJavaScriptとCSSをHTML内にまとめる。
- PDF処理のWebAssembly本体も埋め込み、外部URLから取得せずに初期化する。
- 画面操作を止めないために使うWeb Workerも、配布物に埋め込む。
- その他の必要なフォントや補助データも、外部ファイル参照が残らないように扱う。

ViteにはWorkerを埋め込む機能があり、EmbedPDFにはWebAssemblyのデータを直接渡して初期化するAPIがある。この組み合わせで単一HTML化する案だが、まだ動作検証はしていない。vite-plugin-singlefileだけで全種類のファイルが自動的に埋め込まれるとは扱わない。[ViteのWorker対応](https://vite.dev/guide/features.html#web-workers)、[単一HTML化プラグイン](https://github.com/richardtallent/vite-plugin-singlefile)、[EmbedPDFの初期化方法](https://www.embedpdf.com/docs/engines/introduction)

## 採用前に確認すること

1. **配布形態とオフライン動作**：生成したHTMLを直接開き、キャッシュに頼らず、ネット接続なしで必要な機能が使える。外部通信が発生しない。
2. **ページ編集**：削除・並べ替え・結合・回転後のPDFを保存し、別のPDF閲覧ソフトでも表示とページ構成が正しい。
3. **画像情報・抽出**：寸法と配置サイズが既知のPDFで、ピクセル数・実効解像度・保存した画像を確認する。同じ画像が異なるサイズで配置される場合も確認する。
4. **要素一覧と文字抽出**：日本語を含むPDFで、一覧と抽出結果を確認し、対応できる単位・範囲を明示する。
5. **対象環境**：Mac・WindowsのEdge・Chromeで確認する。開発用サーバーでの成功だけでは、配布HTMLの受入完了としない。
6. **運用上の安定性**：利用するPDFで処理時間・メモリ使用量・配布HTMLのサイズを確認し、採用版を固定する。

## 開発環境の整備（2026年9月19日）

機能開発に先立ち、TypeScript、Vite、vite-plugin-singlefile、pnpmによる開発・ビルド環境を用意した。ESLint、Prettier、Vitest、ブラウザー操作用のPlaywright CLIを追加し、各版はpackage.jsonとpnpm-lock.yamlで固定する。作業手順は[README](../README.md)、検証結果は[verification.md](verification.md)に記録する。

この段階の画面は起動確認用で、PDF機能は含まない。EmbedPDF/PDFiumはまだ導入しておらず、WebAssembly・Worker・補助データの単一HTMLへの埋め込みと、PDFエンジンの採用判断は引き続き未完了。

## 画面案の実装とPDF機能の試作（2026年9月19日）

参照タスク「画面モック案を提案」の2ペイン構成を本体に実装した。白・淡いグレー・緑の配色を使い、左にページ一覧、中央にプレビュー、右側には必要なときだけ画像・文字・要素一覧を表示する。ユーザーの追加確認により、実際のPDFの読み込み・編集・保存までを今回の実装対象とした。

- EmbedPDFの`engines`・`pdfium`・`models`は2.15.0、`fonts-jp`は1.0.0で固定。既存のTypeScript・HTML・CSSを使い、UIフレームワークは追加していない。
- 読み込み・描画・文字抽出・ページ結合は`PdfiumNative`の公開APIを使用。回転の保存・ページ直下の要素列挙・画像の寸法と画素の取得はPDFiumの公開APIを使用する。
- ページ順・削除・回転は画面側の編集状態に保持し、保存時に組み立てる。元のPDFを上書きしない。取り消しは50操作まで。
- プレビューは複数ページを縦に並べてスクロールする。表示位置とページ選択を連動させ、選択中のページを編集・抽出の対象とする。ページ一覧（矢印キーを含む）やページ一覧の上の前後ボタンからも移動できる。25〜300%の倍率と幅合わせに対応し、画面付近のページを倍率に応じて描画する。遠く離れたページのプレビュー画像は解放する。
- Workerをインライン化し、PDFiumのWASMとNoto Sans JP Regularをdata URLとして埋め込む。バイナリは直接復号し、フォントは独自URLから取得せず、エンジンの公開`fontLoader`へ渡す。
- 配布HTMLではCSPの`connect-src 'none'`などで外部通信を禁止する。開発サーバー向けのCSPとは分けている。
- 保存形式は全ページのPDF、選択中ページのPNG・JPEG、個別画像のPNG、ページの文字のUTF-8テキスト。
- ダウンロードの完了・キャンセルは確認できないため、変更状態は文書を開いた時点との差分として保持する。PDFのダウンロード後も、変更が残っていれば「閉じる」で変更破棄の確認を出す。
- 再読み込みに備え、PDF本体・編集状態・選択ページ・倍率・取り消し履歴をIndexedDBへ保存する。HTMLの配置URL（クエリーとハッシュを除く）単位で復元し、明示的に「閉じる」を選んだときに復元用データを削除する。復元用の保存中・失敗時やPDF処理中は画面離脱の確認を残し、保存完了後は再読み込みで復元できるようにする。元ファイルへの書き込みやPDFの自動ダウンロードは行わない。

## toolbox の1つのアプリへの移行と要素の削除（2026-10-18）

- toolbox を1つのアプリに作り直したのに合わせ、PDF の処理を画像変換と共有の PDF エンジン（`src/engine/pdf/`）にした。旧 `src/pdf/runtime.ts` と画像変換の処理を合わせたもの（`runtime.ts`）で、全ツールが同じ Worker を使う。ページは `{ sourceId, sourceIndex, rotation }` で指し、要素の種類は英語の名前（`text`・`path`・`image`・`shading`・`form`・`other`）で返す。文書 id は `crypto.randomUUID()` で作り、ツールの間で重ならないようにする。
- PDFium の WASM と日本語フォントは、`?url&inline` で JavaScript に入れる形をやめ、toolbox の配布物の末尾に gzip で置いて Worker の中で展開する（[toolbox の技術構成](../../../../docs/software-stack.md#1つの-html-にまとめる仕組み)）。文書を読み終える前に取り出すと途中までのデータになるため、PDF エンジンは文書を読み終えてから Worker に渡す（再読み込み直後の復元で起きた不具合を直した）。
- ページの並び・回転・取り消し（`editor.ts`）、倍率とスクロールに合わせた選択（`preview.ts`）、復元用データ（`session-store.ts`）は旧コードとテストを移した。画面は Preact の部品で作り直した。
- 復元用データは、配置 URL ではなく固定のキー（DB `toolbox-pdf-edit`）で持ち、版をまたいで読めるようにした。旧版の記録（DB `pdf-edit-session`）は読まない。
- **要素の削除**：[RFP](RFP.md) の「扱うもの」にありながら初版で保留していた、画像・図形・文字などの要素の削除を足した。PDFium の公開 API（`FPDF_ImportPages` で対象のページだけを新しい文書へ写し、`FPDFPage_RemoveObject`・`FPDFPageObj_Destroy` で要素を除き、`FPDFPage_GenerateContent` で内容を作り直して保存）で、要素を除いた1ページの PDF を作り、新しい元の文書として開いてページを差し替える。元の PDF は変わらず、取り消し・復元・保存はページの差し替えだけで済む。対象はページ直下の要素で、グループ（Form XObject）は中身ごと取り除く。Markdown 変換と OCR は引き続き扱わない。
- ツールの間の受け渡し：ホームや画像変換から PDF を受け取る（開いていれば末尾に加えるか選ぶ）。今のページの並びで書き出した PDF を画像変換へ渡す（ページを画像にする・小さくする）。

## PDF を小さくする（画像変換から移す、2026-10-18）

- 画像変換にあった「PDFを小さくする」を、PDF の作業としてこのツールへ移した。処理は共有の PDF エンジンの `shrink`（`src/engine/pdf/runtime.ts`）で、画像変換にあったときから変えていない。仕上がりは3段階（きれいめ 200 dpi・画質 85、標準 150 dpi・画質 75、小さめ 100 dpi・画質 60）から選び、ページ上の大きさに対してこの解像度より細かい画像だけを縮める。
- 対象：開いている PDF は、今のページの並び・回転・削除で書き出した PDF（「保存」の PDF と同じ）を小さくする。最初の画面とホームからの `shrink` では、選んだ・受け取った PDF を、開いている PDF の編集とは別に小さくする。結果はダイアログの中だけに持ち、復元用データには入れない。保存していない結果があるうちは、閉じる前の確認を出す（`status.guard`）。
- 画像変換へは、ページを画像にするための PDF（`add`）だけを渡す。
- **処理**：各ページの直下の画像オブジェクトを列挙し、条件に合う画像だけを `FPDFImageObj_GetBitmap` で読み、Worker の `OffscreenCanvas` で縮めて JPEG にし、`EPDFImageObj_SetJpeg` で差し替えてから `FPDFPage_GenerateContent` で保存する。文字・図形のオブジェクトには触れない。
  - 差し替えない画像：回転・傾け・反転して置かれたもの、1画素 8 bit 未満（白黒2値のスキャンなど）、透過・色抜きのあるもの（`FPDFImageObj_GetRenderedBitmap` の結果にアルファ値 255 未満がある）、JPEG にしても元のデータの9割以上の大きさになるもの、4,000 万画素を超えるもの、グループ（Form XObject）の中のもの。
  - 複数ページで共有する画像：PDFium は文書内で同じ画像を共有するため、差し替えた後のページでは同じ画像オブジェクトの中身が新しい JPEG になっている。中身が差し替えた JPEG と一致する画像は、`FPDFPageObj_Transform`（単位行列）で変更済みにしてからページの内容を作り直し、元の画像への参照を新しい画像に向ける。こうしないと元の画像が残り、容量が減らない（[画像変換の検証記録](../../image-converter/docs/verification.md#実装前の-pdfium-の確認2026-10-03)）。
  - ページの内容を作り直すため、PDF の作りによってはしおり・フォーム・注釈などの残り方が元の PDF と変わる場合がある。

## 現在の状態と未決事項

- 実装・改修は標準機能とライブラリを優先する[toolboxの共通方針](../../../../docs/development.md#実装方針)に従う。共通部品（`src/ui/`・`src/lib/`・`src/app/`）を使い、PDF固有の保存形式・編集状態はこのツールで管理する。

- 実PDFを扱う試作と、WASM・Worker・日本語フォントを含む単一HTMLビルドを実装した。合成PDFでのページ編集・保存再読込・描画結果の一致・日本語文字抽出・既知の画像情報を自動検査する。
- 要素一覧の単位はPDFページ直下のオブジェクト。グループはグループとして表示し、内部の画像を再帰的に抽出する機能は未対応。画像の配置サイズ・dpiは画像の変換行列から計算する。
- 個別画像はデコードした画素をPNGに保存する。マスク・切り抜き・複雑な色空間の完全再現は未保証。ページ全体のPNG・JPEG保存も利用できる。
- パスワードが必要なPDFは未対応。PDF保存時のしおり・電子署名・文書単位の付加情報の保持は未保証。日本語代替フォントはRegularのみ。
- `file://`起動、キャッシュなしの完全オフライン、Windows・Edge、他のPDF閲覧ソフトでの確認、大容量・多様な実務PDFの安定性は引き続き受入対象。現在の検証結果は[verification.md](verification.md)を参照する。
- PDFエンジンは試作への導入段階であり、正式採用の判断は対象環境での受入後に行う。保留した機能の範囲は変更しない。
- PDFを小さくする：実際の写真・スキャンの多い PDF で容量が減り、文字の選択・検索が保たれるか（合成 PDF では確認済み）。特殊な色空間・ICC プロファイル付きの画像の色、しおり・フォーム・注釈の残り方は未検証。
